# Private SEI schema provisioning

These are operator scripts, never application startup migrations. Run `000-sei-app-role.sql`, `001-sei-hosted.sql`, `002-sei-study.sql`, `003-sei-ai-feedback.sql`, then `004-sei-auth.sql`, in that order as `postgres` in the intended project. All can be run again; 000 preserves a configured login/password but refuses unsafe role attributes or memberships. Set the role's password and enable LOGIN out-of-band. There is no password in these files and no role membership grant.

001 refuses existing `sei` objects owned by an app/API role, because ownership can disable RLS and triggers. The function ownership checks in 001 and 002 include `sei.request_owner_id()` on reruns. 001 removes any schema CREATE grant from `sei_app` before granting USAGE. Every future migration must explicitly revoke public/API privileges on its objects too; schema-local default privileges cannot override PostgreSQL's global defaults.

001 defines the operator-owned `sei.request_owner_id()` before any policies. This stable SQL SECURITY INVOKER function fixes `search_path` to `pg_catalog` and returns `nullif(current_setting('request.jwt.claim.sub', true), '')::uuid`. Missing or empty claims return NULL, so owner policies return no rows and reject inserts. PUBLIC execution is revoked and `sei_app` receives EXECUTE. Both migrations use this helper for every owner policy; they require no access to the `auth` schema or changes to Supabase-managed privileges.

Keep `sei` private and absent from exposed Data API schemas. Only the server connects as `sei_app`; clients cannot connect directly as that role or obtain its credentials. Only server-side `withOwnerTransaction` sets claims transaction-locally, using the configured owner in public mode, verified JWT claims in JWT mode, or the session account owner in password mode. The helper reads those claims; it does not verify identity itself. The migrations never create or change objects in `public`, `auth`, `storage`, or `lesson_planning`.

The disposable Postgres harness creates only an admin-owned decoy `auth` schema with no PUBLIC or `sei_app` access and no functions. It asserts that `sei_app` has no USAGE there after running each migration twice. The existing owner operations, other-owner isolation, absent-claim read/insert denial, and COMMIT/ROLLBACK claim-clearing assertions run with that restriction.

The study, native and AI tables force owner RLS; config, content, task versions, attempts, judgments, and evidence/events additionally reject update, delete, and truncate. Only native projections, study drafts and AI usage permit UPDATE. Projections can be rebuilt from verified immutable events. The app does not receive DELETE or TRUNCATE privileges.

004 adds `accounts` and `auth_sessions` with forced RLS and no direct table privileges for `sei_app`, PUBLIC, `anon`, or `authenticated`. Seven operator-owned SECURITY DEFINER functions with fixed `pg_catalog` search paths provide narrowly scoped authentication operations. The `sei_auth_definer` policy permits the migration operator to execute these functions even under FORCE RLS; only `sei_app` receives EXECUTE. Run reruns as the same operator. The first registration serializes on `accounts` and uses `PUBLIC_OWNER_ID`, preserving the existing owner history without copying it. Later accounts get independent UUIDs only when sign-up is enabled. Migration 004 does not change `sei.request_owner_id()` or existing owner policies. See [hosted mode](../../../../../docs/hosted-mode.md) for environments and operator setup.
